# 03 · 让任务清单能够恢复

<p class="eyebrow">STAGE 03 / 对话会变短，工作不能失踪</p>

一个长任务不应只存在于模型刚刚写下的一段话里。本章给 Agent 加上持久化任务清单：任务有稳定 ID、状态和版本，重启后还能读回。清单记录工作进度，不负责证明工作真的完成。

## 无 Key 逐章实验

这条命令使用真实 Pi 与脚本化 Provider，生成独立练习目录并断言本阶段行为；不调用远程模型。

```sh
npm run stage -- --stage 3
```

## Pi 已有什么，为什么还要存任务

Pi 已有会话持久化，扩展也可以用 `appendEntry()` 保存自定义条目。官方扩展示例展示了这种做法。我们选择另一种明确的教学边界：把任务清单存成工作区内的结构化快照，让它跨会话可恢复，并能独立测试损坏与并发问题。会话记录解释“说过什么”，任务清单解释“接下来做什么”。

这个选择有代价：Pi 会话切换或分支不会自动回滚任务文件。任务清单属于工作区，不属于某个对话分支；不要把二者混为一谈。

## 运行第三阶段

```sh
npm run agent -- --stage 3 --workspace examples/workspaces/todo
```

让 Agent 创建三个任务：“读测试”“修复实现”“验证并审查差异”。然后输入 `/tasks`。退出，再用同样的工作区重启，检查 ID 与状态是否保留。

任务元数据可在计划模式写入。真正修改项目源码仍需要执行模式和审批。让模型把第一项标为 `in_progress`，再同时启动第二项；存储层应拒绝第二个活动任务。这个课程约束使主 Agent 的工作焦点清楚，不代表所有任务系统都只能串行。

## 数据模型和存储责任

阅读 `src/core/tasks.ts` 的 `TaskState`：

```ts
export interface TaskState {
  version: 1;
  revision: number;
  tasks: Task[];
}
```

`version` 用于未来格式迁移，`revision` 记录成功变更次数，`id` 则用于稳定定位任务。数组下标不能承担 ID 的职责，因为插入和排序会改变它。

一次变更经历：读取并验证旧状态 → 计算新状态 → 写旧状态备份 → 原子替换新快照。`atomicWrite()` 使用临时文件、同步和重命名，避免读者看到半个 JSON。进程内按文件路径排队，避免同进程两个实例互相覆盖。**它没有实现跨进程锁**，所以不要让两个独立 Agent 同时写同一份任务状态。

```ts
const task = await store.add("Inspect failing tests");
await store.update(task.id, "in_progress");
await store.update(task.id, "done");
```

这是实际 `TaskStore` API 的调用顺序。工具注册层把模型参数转成这些方法；业务规则留在存储层，既服务模型工具，也服务测试。

## 恢复不是掩盖错误

主快照读不出时，存储尝试验证 `.bak` 并恢复最后一份可读状态。它可能比最近变更落后一版，不能宣称“零数据损失”。如果主文件和备份都损坏，应明确失败，而不是返回空任务列表制造“工作完成”的错觉。

同理，`done` 只表示工具接受了状态变更。测试通过、diff 审查和实际行为还需要独立证据。第 07 章会把这些证据连接进工作流。

## 实验与故障检查

运行 `npm test`，重点读任务恢复、无效状态、重复活动任务和同进程并发变更测试。测试在临时目录制造损坏，不需要破坏你自己的工作区文件。

做一次人工恢复实验：创建任务，记下 ID，退出并重启 `/tasks`。再问模型“哪些任务已经验证过，依据是什么？”如果只有状态没有测试结果，合理回答应承认缺少证据，而不是把勾选当成证明。

**验收标准：** 清单跨重启恢复；非法状态不会写入；损坏主文件可从有效备份恢复；无可用备份时显式失败。

## 设计对应

任务面板常给人一种 Agent 正在有序工作的感觉。本课程强调面板背后的契约：稳定身份、可验证状态转移和持久化边界。它对应编程 Agent 的进度管理需求，但不声称复制 Codex 或 Claude Code 的内部任务存储格式。

## 进程在动作完成后崩溃：先核对，再恢复

```sh
npm run recovery:demo
```

这个无 Key 实验在 macOS / Linux 上启动两个独立进程，使用**官方脚本模型驱动真实 Pi 0.85.1**。所有练习文件、会话和虚构收据都在新建的 `.cache/recovery/pi-*/` 中；不会发送真实消息或调用远程模型。入口是 `scripts/recovery-lab.ts`，子进程在 `scripts/recovery-worker.ts`。

实验先准备一个 `done` 任务和一个 `in_progress` 任务。Pi 的第一个固定 `bash` 操作以退出码 7 拒绝虚构投递，实际工具错误会写进会话。第二个操作追加一条 `delivery-001` 收据，并把 `draft.txt` 改成 `delivered`。这一步故意**不是幂等的**：再次执行会追加第二条收据。

动作结束后，实验在成功工具结果的 `message_end` 回调中向当前 Pi 进程发送 `SIGKILL`。锁定版本的 [AgentSession 源码](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/agent-session.ts) 先通知会话订阅者，再调用 `sessionManager.appendMessage()`。实验同时检查实际落盘 JSONL，而不只依赖这个源码顺序：

| 崩溃后的证据 | 实际观察 | 可以推断什么 |
| --- | --- | --- |
| 任务清单 | `done`、`in_progress` | 清单保留了进度，没有替动作做最终判定 |
| 失败工具结果 | `isError: true` | 第一次调用确实失败 |
| 成功调用对应的会话 | 有 `toolCall`，没有该 `toolResult` | 仅凭会话无法判定动作是否完成 |
| 独立虚构收据 | `delivery-001` 恰好 1 条 | 这次本地动作确实已经完成 |

恢复进程先由宿主读取并核对收据，再以新用户消息把事实交给脚本模型。它用 `--resume` 背后的同一个 SDK 机制继续原对话，保持默认 `plan` 模式，只调用 `task_update` 将任务置为 `done`。验收断言恢复前后收据计数都为 1，并检查真实执行列表只有 `task_update`。生产 `TaskStore` 仍只有 `pending / in_progress / done`；工具失败和动作完成证据分别保存在工具结果与收据中，不伪造一个任务 `failed` 状态。

最后，宿主恢复最初的文件 checkpoint：`draft.txt` 回到 `pending`，但任务仍为 `done`，会话和收据都不回退。收据放在 checkpoint 排除的 `.learn-pi/recovery/`，模拟独立的业务事实；模型的 `read` 仍不能读取课程元数据。文件回滚不代表已经发生的投递被撤销。

这是一个**固定样例的收据核对策略**，不是 Pi 通用的 exactly-once 保证。实验制造的是进程终止，不是断电；收据内容由本地固定脚本生成。面对没有可核对结果的动作，缺失工具结果应保留为待确认，不能据此盲目重放。原始会话留在忽略的练习目录，公开汇总只记录断言与计数。
